# ADR 0008: vLLM over Ollama for model serving
Status: Accepted
Date: 2026-10-08
Related docs: [llm-serving](../architecture/llm-serving.md), [models](../architecture/models.md), [observability](../architecture/observability.md), [ADR 0023](0023-ollama-local-vllm-server.md)

## Context
Several agents may run in parallel and several users may ask questions at once. Ollama serves requests largely one at a time, so concurrent agents queue behind each other. The GPU is on VM 4 ([ADR 0002](0002-on-premises-vms.md)). Dashboards must not depend on the LLM at all; the 500 ms target applies to non-AI reads from Postgres/Redis ([corrections](../context/corrections.md) item 3). vLLM's benefit is concurrency for AI features.

## Decision
Serve the private LLM on the GPU server with vLLM. vLLM uses **continuous batching**, merging tokens from many requests into shared GPU passes, and exposes an OpenAI-compatible API (`http://<internal-ip>:8000/v1`), so LangGraph code only changes `base_url`. Example from the notes: `docker run --gpus all -p 8000:8000 vllm/vllm-openai:latest --model meta-llama/Llama-3.1-8B-Instruct` (model choice is TODO).

GPU memory facts: an 8B-parameter model needs roughly 16 GB at 16-bit precision and roughly 5-6 GB when 4-bit quantised (the "6 GB" figure in an early note is the quantised size). Extra memory is needed for the KV cache, which grows with the number of concurrent requests and context length. Parallel agents do not multiply model memory but need KV cache headroom. Monitor vLLM KV cache utilisation. Typical GPUs: NVIDIA L4 (24 GB), A100 (40 or 80 GB); TODO: confirm GPU with IT. Quantisation is not done by us; download pre-quantised AWQ or GPTQ models if needed. ## Alternatives considered
**Ollama.** Strengths: easiest to start, great for laptops. Why it lost on the server: poor concurrency. It is still used for local development ([ADR 0023](0023-ollama-local-vllm-server.md)).

**Hosted APIs.** Strengths: strongest models, no GPU to run. Why it lost: data leaves the network unless security approves (TODO).

**TGI or other serving options.** Strengths: viable servers with similar features. Why it lost: vLLM is the widely used default; no reason to deviate.

## Consequences
Positive: concurrency for many users and agents; OpenAI-compatible client code that is identical to local development apart from configuration.
Negative: needs an NVIDIA GPU server and Docker with GPU support; GPU memory planning; model weights must reach an on-prem server.
Obligations: monitor KV cache; evals must pass on staging (vLLM); show "AI unavailable" when the server is down.

## When to revisit
GPU capacity limits, or a better serving option.
